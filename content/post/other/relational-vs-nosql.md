## 关系型数据库

### 概念

关系型数据库是指采用关系模型来组织数据的数据库。简单来说，关系模型就是二维表格模型：数据存放在表的行和列中，表与表之间通过主键、外键建立关联，用 SQL 查询。

主要代表：PostgreSQL、SQLite、MySQL、Oracle、SQL Server。

### 优点

1. 容易理解：二维表的结构贴近现实世界中的表格，容易理解。
1. 使用方便：通用的 SQL 语句使操作关系型数据库非常方便，Join、聚合、子查询等复杂查询都有成熟支持。
1. 数据一致：通过范式化设计减少数据冗余，通过事务的 ACID 特性保证数据一致性。

### 瓶颈

1. 海量数据的读写效率：网站并发量高时，每秒可能有上万次请求，单机数据库的磁盘 I/O、CPU 和连接数都会成为瓶颈。
1. 高扩展性和可用性：在 Web 架构中，数据库通常是最难横向扩展的一层。应用服务器可以简单地加机器、加节点，单机关系型数据库则做不到，写入扩展尤其困难。

关系型数据库的写入要维护事务：先写 WAL（redo log）、维护 undo 信息、更新索引，再在合适的时机刷盘。这些开销换来了崩溃恢复和一致性，但在写入量特别大的场景下会成为负担。

## 从关系型到非关系型

关系型数据库最大的优点是事务的一致性，这使它适用于一切对一致性要求高的系统，比如银行系统。

但在很多 Web 应用中，对一致性的要求没那么严格，允许数据在短时间内不一致（[最终一致性](../cs/database/transaction.md#最终一致性)），关系型数据库的这个特点就没那么重要了。相反，为了维护强一致性付出的代价，是读写性能和扩展性受限。像微博、Facebook 这类应用，对并发读写和水平扩展的要求极高，单纯靠关系型数据库难以应付，于是非关系型数据库应运而生。

关于读压力，可以把读和写分开处理：

- 写入（编辑、下单、保存）仍走关系型数据库，享受事务和约束。
- 读取（浏览、列表、详情）通过缓存（[Redis](../cs/redis.md)）、只读副本、CDN 或发布时生成的静态页面来承接，大部分访问不会落到主库上。

这种做法适合更新频率不高、能接受一定延迟的数据，比如文章、商品目录；库存、价格、账户余额这类对时效要求高的数据要另外考虑缓存失效和一致性。

## 非关系型数据库（NoSQL）

### NoSQL 的概念

NoSQL 泛指不以关系模型为核心的数据存储系统，通常为分布式和水平扩展而设计，很多产品默认放宽了一致性来换取性能和可用性，背后的理论是 [CAP 与 BASE](../cloud/cap.md)。主要代表：Redis、MongoDB、Cassandra、CouchDB。

NoSQL 不要求固定的表结构。以文档数据库为例，同一个集合里的每条记录可以有不同的字段；把相关数据存在一起后，读取一个用户的信息不需要像关系型数据库那样做多表 Join，按 key 或 ID 一次取出即可。

### NoSQL 命名的含义

NoSQL 并不是「完全不用 SQL」，而是不以关系模型为核心。NoSQL 的字面含义经过了演变：

- 早期理解为 "No SQL"，意指不使用 SQL。
- 后来业界更倾向解读为 "Not Only SQL"，即「不只是 SQL」，强调对关系型数据库的补充而非替代。

区分一个数据库是不是 NoSQL，关键看数据模型（是否以关系/表来组织数据），而不是查询语言的语法。事实上很多 NoSQL 数据库都提供了类 SQL 的接口，例如：

- Cassandra 有 CQL（Cassandra Query Language），语法与 SQL 非常接近。
- MongoDB 持续增强聚合查询能力。

另外，ClickHouse 这类列式分析数据库也支持 SQL，但它面向 [OLAP](./olap.md) 分析，通常单独归为「列式数据库」，不和上面这些 NoSQL 放在一起比较。

### 分类

| 类型 | 特点 | 代表 |
| --- | --- | --- |
| 键值（Key-Value） | 按 key 读写，并发读写性能极高，常用作缓存、会话、计数器 | Redis、Valkey、Amazon DynamoDB |
| 文档（Document） | 以 JSON/BSON 文档存储，结构灵活，支持按字段查询和建索引 | MongoDB、CouchDB |
| 宽列（Wide-Column） | 面向海量数据和水平扩展，写入吞吐高，底层多为 [LSM-Tree](./lsm-tree.md) | Cassandra、HBase |
| 图（Graph） | 以节点和边存储关系，适合社交关系、推荐、知识图谱 | Neo4j |

### NoSQL 的缺点

1. 查询能力因产品而异：键值数据库基本只能按 key 访问，不支持按字段条件查询；文档数据库支持按字段查询和二级索引，但跨集合 Join 通常比关系型数据库弱。
1. 事务支持有限：不少 NoSQL 只保证单条记录（单个文档、单个 key）的原子性。MongoDB 从 4.0 起支持多文档事务，Redis 有 `MULTI`/`EXEC`，但整体上不如关系型数据库成熟。
1. 一致性要自己权衡：默认最终一致的系统，需要业务能接受短暂的不一致，或显式选择更强的一致性级别。

## 对比

### 存储方式

关系型数据库以表的形式存储。例如存储用户及其订单，订单表通过外键关联用户表：

```sql
CREATE TABLE users (
    id   BIGINT PRIMARY KEY,
    name TEXT NOT NULL
);

CREATE TABLE orders (
    id      BIGINT PRIMARY KEY,
    user_id BIGINT NOT NULL REFERENCES users(id),
    amount  NUMERIC(10, 2) NOT NULL
);
```

NoSQL 则按数据模型不同而不同。键值数据库按 key 存取 value，文档数据库常把相关数据嵌套在一个文档里：

```json
{
  "_id": 1,
  "name": "Alice",
  "orders": [
    { "id": 1001, "amount": 99.00 },
    { "id": 1002, "amount": 25.50 }
  ]
}
```

### 事务

在关系型数据库中，如果多张表需要在同一批次更新，可以放在一个事务里：所有操作完成后统一提交，其中一步失败则全部回滚。

NoSQL 早期大多只保证单条记录的原子性，靠把相关数据放在同一个文档或同一个 key 里来规避跨记录事务。现在 MongoDB 等产品已支持多文档事务，但会带来性能开销，设计时仍倾向于让一次写入只涉及一条记录。

### 数据表 vs 数据集

关系型数据存储在表的行和列中，表之间彼此关联，容易按需组合提取；非关系型数据通常把一整块相关数据存在一起，按整体读取。

### 预定义结构 vs 动态结构

在关系型数据库中，必须先定义好表结构（字段、主键、索引、外键等）才能添加数据。表结构可以在定义后修改，但大表的结构变更往往比较麻烦。

在 NoSQL 数据库中，数据结构不需要预先定义，可以随时添加新字段。不过 schema 并没有消失，只是从数据库转移到了应用代码里，需要应用自己保证数据格式的一致。

### 规范化 vs 反规范化

关系型数据库倾向于规范化：把数据拆成最小的逻辑表来避免重复，节省空间、方便维护一致性，代价是多表之间的关系让查询和管理变复杂。随着磁盘越来越便宜，节省存储空间的意义已经不如从前。

非关系型数据库倾向于反规范化：数据经常重复存储，相关数据存成一个整体，整块读取效率更高，代价是更新时要同步修改多处副本。

### 纵向扩展 vs 横向扩展

传统关系型数据库主要靠纵向扩展（换更强的机器）来提升处理能力；读压力可以通过只读副本分担，写压力则要靠[分库分表](../cs/database/db-split.md)（如 Vitess、Citus）。也有 TiDB、CockroachDB、Google Spanner 这类分布式 SQL 数据库，在保留 SQL 和事务的同时支持横向扩展。

大多数 NoSQL 数据库在设计时就考虑了分布式，可以通过加节点、分片来横向扩展，实现负载均衡。

### 其他方面

关系型数据库使用 SQL 查询，NoSQL 各自提供 API 或查询语言，访问方式更简单直接，但不统一。

成本和许可上，两边都有开源和商业产品：PostgreSQL、MySQL、SQLite 是开源的关系型数据库，Oracle、SQL Server 是商业数据库；NoSQL 方面，MongoDB 使用 SSPL 许可，Redis 在 2024 年改为非开源许可后，Redis 8 又加入了 AGPL 选项，社区也分叉出了 BSD 许可的 Valkey。选型时要留意许可证。

## 如何选择

很多大型互联网应用会采用「关系型数据库 + NoSQL」的组合方案，例如 PostgreSQL/MySQL 存核心业务数据，Redis 做缓存，因为两者各有优缺点。

关系型数据库适合存储结构化数据，比如用户账号、地址、订单：

1. 这些数据通常需要结构化查询，比如 Join，这时关系型数据库更有优势。
1. 这些数据的规模、增长速度通常是可以预期的。
1. 对事务性、一致性要求高，数据关系比较复杂。

NoSQL 适合存储结构灵活或访问模式简单的数据，比如文章、评论、日志、缓存：

1. 结构经常变化，或每条记录的字段不尽相同。
1. 数据量大，增长速度难以预期，需要横向扩展。
1. 按 key 获取数据效率很高，但对 Join 等复杂查询的支持较差。
