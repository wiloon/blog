我的日常开发机是一台 MacBook Air，家里还有一台 AMD CPU 的 Linux 主机，一直闲着。同时我订了三家的 AI：Claude、ChatGPT（Codex）和 Cursor，每家大约 20 美元一个月，各自有每周配额。

结果是：Mac 上同时跑几个 Agent 再加上测试，CPU 和内存就不够用；Linux 主机却在吃灰。

所以我写了 baton，把 Agent 的工作搬到那台闲置主机上，让三家的 Agent 分工、互相评审，并且按每家剩余的配额派活, github 仓库在这: https://github.com/wiloon/baton

## 它做什么

我在 Mac 上和 Claude Code 一起把需求写成 GitHub Issue，需要的话附上 ADR，然后给 Issue 打上 `ready-for-agent` 标签，后面就不用管了。

Linux 主机上的 systemd 定时器每十分钟唤醒 baton 一次，每次把某个 Issue 或 PR 往前推进一步：

1. 评审设计：一个 Agent 检查 Issue 是否清楚到可以开工，提出问题；另一次运行根据问题修订 Issue。直到没有问题。如果超过轮数上限，或者有需要我来定的分歧，就打上 `ready-for-human` 标签等我处理。
2. 开发：在独立的 git worktree 里写代码、跑检查、推送分支、开 PR。
3. 评审 PR：由没有参与写这个 PR 的厂商来审。
4. 修复：根据评审意见修改，同样有轮数上限。
5. 合并：CI 通过，并且 PR 里写明不需要手动测试，就自动合并；否则交给我。

一次唤醒做完一步后，如果还有下一步可以直接做，会接着做，有次数上限。

## 为什么让不同厂商互相评审

同一个模型评审自己写的东西，不容易发现问题。让 Codex 审 Claude 写的设计，让 Claude 审 Cursor 写的代码，相当于每次都有一个不同来源的第二意见。

baton 选评审者时，会排除参与写过这个 PR 的厂商。只有三家都参与过的时候，才退一步，用同一家厂商的另一个模型来审。

## 按配额派活

每次要运行 Agent 之前，baton 先排除这几类厂商：撞到用量上限或登录失效、正在冷却的；超过配置的配额上限的；做评审时会排除参与写过这个 PR 的。

剩下的厂商里，选离本周均匀消耗进度落后最多的那家。比如 Cursor 这周的配额用完了，活就自动落到 Claude 和 Codex 身上。配额数据从各家的 CLI 读取，数据过期时会发一次很短的探测调用来刷新。

我想要的效果是三份订阅在一周里平稳地用完，不浪费，也不提前耗尽。

## 人在哪里

我不希望它变成一个全自动乱合并的机器人。需要判断的地方都会停下来，打上 `ready-for-human` 等我：设计上的分歧、需要手动验证的改动、修复超过轮数上限的 PR。

反过来，我也可以给自己写的 PR 打 `agent-review` 标签，请它们评审；或者在 Agent 开的 PR 上留言，再打 `agent-fix` 标签，让它们按我的意见修改。

## 安全边界

无人值守地运行 Agent，本质上是在主机上执行模型生成的代码，包括被监控仓库自己的测试。baton 给 Claude Code 加了 PreToolUse hook 和权限配置，Codex 用它自己的沙箱，Cursor 在只读运行之后检查有没有产生改动。这几种控制覆盖范围不同，都不等于主机隔离。

所以我的建议是：用专用账号，在可以随时重建的主机或虚拟机上运行，凭据只开放给被监控的仓库。具体的信任边界写在仓库的 SECURITY.md 里。

## 我不确定的地方

现在 baton 的调度全部是写死的规则：固定的任务优先级、固定的厂商选择方式、固定的轮数上限。我不确定这是不是合适的做法.

1. 或许有些决策适合交给 LLM？比如「这个设计分歧值不值得打扰我」「这个任务该给哪一家」。哪些必须保持确定性？
2. 我目前的想法是：任务准入、状态流转、执行权限保持确定性，只在模糊的地方让模型给建议，并且先用只记录、不执行的方式，和现有规则对比一段时间。
3. 我调研过 Agent Orchestrator、Paperclip、Gas Town 等项目，调研笔记在仓库的 docs/research 目录里，但还没有实际试用。
4. 按「本周均匀消耗进度」派活这个策略，有没有更好的做法？

欢迎提 Issue、PR，或者直接回复我。如果你也有一台闲置的机器和几份 AI 订阅，可以试试看，安装步骤在 README 里。
